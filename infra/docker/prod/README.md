# Single-host class deployment with HTTPS

The production Compose overlay builds the existing backend Dockerfiles and a static Angular/Nginx frontend in the separate `7irafi-prod` Compose project. The frontend Nginx terminates HTTPS with a self-signed certificate generated by OpenSSL for the deployment machine's IPv4 address. The application, API, and WebSockets use `https://<IP>`; media uses `https://<IP>:9443`. HTTP port 80 redirects to HTTPS, apart from the health probe. Backend services, PostgreSQL, Kafka, and MinIO have no published host ports. No external TLS proxy or domain name is needed for this class-project setup.

Production HTTP API requests use the `/api/` prefix for all route families: auth, users, jobs, applications, ratings, conversations, notifications, analytics, and status. Nginx removes `/api` before forwarding to the gateway, so `/api/jobs` reaches `/jobs` and `/api/status` reaches `/status`. Angular page URLs such as `/jobs`, `/applications`, `/conversations`, and `/status` use the SPA fallback for direct links and refreshes. WebSocket paths remain `/ws`, `/notifications-ws`, and `/ws/analytics`. Development continues to call the gateway directly using its existing API base URL.

## Before the first deployment

1. Install Docker Compose 2.24.4 or newer (the overlay uses `!reset` and `!override`) and OpenSSL 1.1.1 or newer with `-addext` and `-verify_ip` support on the deployment host. On macOS, set `OPENSSL_BIN` in `.env` to your Homebrew OpenSSL executable if the system version lacks these options, for example `/opt/homebrew/opt/openssl@3/bin/openssl`.
2. Copy `infra/docker/prod/.env.example` to `infra/docker/prod/.env` and replace every credential placeholder. Use a distinct production PostgreSQL volume and keep `KAFKA_CLUSTER_ID` stable while reusing the Kafka volume. Never commit `.env`.
3. Leave `TLS_HOST_IP=auto` to use the IPv4 address selected by the host's default network route. Linux uses `ip route get`; macOS uses `route` and `ipconfig`. If a VPN or another network is selected, set `TLS_HOST_IP` to the address reachable by the demo devices, for example `192.168.1.20`. An environment override such as `TLS_HOST_IP=192.168.1.20 make prod-up` also works. Keep `TLS_HOST_IP` and `OPENSSL_BIN` values unquoted in `.env`. Prefer a DHCP reservation or static address for the demo.
4. Allow connections to host TCP ports 80, 443, and 9443 on the demo network and ensure no other service already owns them. A LAN IP requires clients to be on the same network or have a route to it.
5. Configure a copy of database backups **off this host**. The included `postgres-backups` Docker volume protects against a database volume failure, but not loss of the host. Verify a restore using the existing `infra/backup/restore.sh` in a disposable environment. Uploaded MinIO objects need a separate backup plan.
6. Run `make prod-up`. It prepares HTTPS, runs read-only preflight checks, initializes missing logical databases, builds and starts the stack, waits for healthy services, and validates the running Nginx configuration. Flyway applies each service's pending migrations at startup.
7. Import `infra/docker/prod/tls/server.crt` into the appropriate OS/browser trust store on every demo machine. Trust setup depends on the browser and OS; it is not performed by the scripts. Share only the public certificate, never `server.key`. Both HTTPS ports use the same certificate. Accepting a warning on the app alone may leave media requests blocked, so establish trust for both origins before the demo.
8. Open the application URL printed by the preparation script. Check `make prod-ps`, `/status` (the Angular page), `/api/status` (the JSON endpoint), registration, job posting, applying, image display, and messaging. Use `make prod-logs` if a service is unhealthy.

For later releases, run `make prod-backup` before `make prod-up`. Restore is intentionally manual because it overwrites data. The `prod-up` target builds the current source on the deployment host; use a CI image registry and pinned image digests before scaling this beyond a single host.

## HTTPS preparation and certificate lifecycle

`make prod-https` runs `prepare-https.sh` without starting Docker. It generates a certificate valid for 365 days with the selected IPv4 address in its Subject Alternative Name (SAN), stores the certificate and private key in `infra/docker/prod/tls/`, and writes `.env.https` beside the production `.env`. The private key has mode 600 and the TLS directory has mode 700. These files are excluded from Git and the frontend Docker build context. Certificates are mounted read-only into Nginx and are never baked into its image.

The generated `.env.https` contains the selected IP, `FRONTEND_ORIGIN`, `S3_PUBLIC_ENDPOINT`, and certificate fingerprint. All production Compose commands load the credential `.env` first and the generated settings second. Ambient shell values for those generated keys are cleared so preflight, startup, logs, and backups use the same origins and fingerprint. Existing credentials are not rewritten.

Preparation reuses the certificate while it remains valid for the selected IP and the private key file exists. A missing key, invalid/expired certificate, or changed IP triggers generation. A changed certificate fingerprint makes Compose recreate the frontend during `make prod-up`, so Nginx loads the new certificate. If a directly trusted self-signed certificate is replaced, install/trust the replacement on the demo machines again.

Certificate checks run when `make prod-https` or `make prod-up` is invoked; there is no background renewal scheduler. `make prod-preflight` checks credentials, required HTTPS files, and the Compose model. Nginx validates the certificate/private-key pairing when it starts. Run preparation before invoking preflight or other production commands on a fresh checkout.

`prepare-https.sh` gets the IP, creates or reuses the certificate directly in Nginx's mounted TLS directory, and writes the HTTPS settings. No certificate copy step is needed. Run one preparation or deployment command at a time.

Nginx proxies media to the internal MinIO API without rewriting its path or query string and forwards the original host including `:9443`, as required by signed object URLs. Its `/healthz` endpoint on HTTP returns a simple success response for Docker's healthcheck without requiring browser trust or disabling TLS verification.

## Data setup

The Postgres init script creates one logical database per data-owning service. Job skills/cities and professional categories/cities are reference data inserted by versioned Flyway migrations. They are not a separate repeatable `seed` command. Add disposable demo records only in a development-only script; never run those against production.

## Limits

Self-signed certificates require explicit client trust and are intended for this class deployment. Publicly trusted certificates and a domain can be added for a public deployment. This remains a single-host setup, with no host-failure redundancy. Off-host backups, production monitoring, and alert delivery need their own operational configuration; observability services are optional and must be enabled for the production Compose project. No backend source is changed by this overlay.
